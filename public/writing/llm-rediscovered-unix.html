Aesop · Field Note

An LLM rediscovered Unix

Not from the papers. From the one rule it could never break — the machine can be wiped at any moment.

On a design that fell out of a survival constraint, and why the same idea keeps solving the AI industry's hardest problems.

Aesop is a crash-only harness for running fleets of AI coding agents. But it didn't start as an architecture. It started as a constraint — and the architecture is what was left standing after everything fragile got knocked down.

The constraint was blunt: assume the box can be erased between one step and the next. A security agent quarantines your files. A session dies mid-thought. A process is killed with no warning. The number-one rule written down before any code was: the system's memory must survive its own destruction.

Cardinal rule №1

"Nothing important lives in RAM. If it matters, it is a file on disk, in git, that a fresh process can re-read and continue from."

Follow that rule honestly and you don't get a clever framework. You get Unix. Every decision below was forced by "it can be wiped," and every one turns out to have a name that predates the LLM by fifty years.

The constraint, and what it forced

Survival rediscovered the primitives

Read the left column as the practical problem "it can be wiped" creates. Read the right as the Unix principle that is the only real answer to it.

The constraint

State can vanish, so it can't live in a running process.

The principle

everything is a file. STATE, the build log, the tracker, receipts — plain, diffable text on disk. The mind is inspectable with cat and grep.

The constraint

Restart is not an exception — it's the normal case.

The principle

crash-only recovery. There is no graceful shutdown because there's nothing in memory to save. Recovery is: re-read from disk, continue. Logs are append-only; every step is idempotent.

The constraint

Any worker might die, so no worker can be precious.

The principle

stateless processes over durable state. Agents are filters: read a task + the repo, emit a diff + a report, keep nothing. Kill one, respawn it, lose nothing.

The constraint

The thing that decides shouldn't be the thing that acts.

The principle

mechanism vs. policy. A worker seat executes; an orchestrator seat judges. Separated, each can be swapped without touching the other.

The constraint

A broken step must never masquerade as a good one.

The principle

exit codes, fail-closed. The secret-scan gate exits non-zero and the push dies. Errors block; they never silently pass. Success is a status code, not a vibe.

The constraint

Parts get replaced; the seams have to hold.

The principle

the narrow waist. One driver contract, like a device file: any model behind it presents the same "run this, return a Report" interface. Swap the model; the shape doesn't move.

Nobody sat down to implement Unix. The rule "it can be wiped" is a filter, and these are the only designs that pass through it.

The same idea, over and over

One primitive, four problems

The reason this is worth writing down: the pattern wasn't designed once and applied once. It kept re-solving different problems, and each time the shape was identical — a stateless watcher or worker, running over durable files, that recovers by re-reading. That repetition is the whole thesis.

  1. First

    An IOC monitor

    Watch for indicators of compromise, write findings to an append-only log, survive a restart. A small tool that owns one job and keeps its state on disk. It worked because it assumed it could die.

  2. Then

    A drift monitor

    Same shape, new target: instead of watching for intruders, watch the system for drift from its own rules — stale docs, broken gates, files that no longer match the numbers they claim. Auto-fix the safe cases, propose the rest. It was the IOC monitor with a different lens.

  3. The realization

    The Conductor

    If a monitor is just a stateless process over durable state, then so is an orchestrator. The whole fleet — workers, reviewers, watchdogs — is monitors and filters composed over git. The orchestration project was the monitor pattern all the way up.

  4. Now

    Aesop

    Conductor, refactored into a portable, source-available microkernel: a tiny fixed core, with the model in each seat as a swappable part. The kernel doesn't get smarter; it stays small and correct, and lets you drop in whichever model you want as userland.

The microkernel

The model is a replaceable part

A microkernel keeps almost nothing in the privileged core and pushes everything replaceable out to userland. Aesop's core is the state layer and the gates — the parts that must be correct. The models are userland. As of 0.4.0 you rebind either seat from one config block, the way you'd set CC=clang or $SHELL: config indirection, no code change.

# two seats; swap the model in either without touching code
"seats": {
  "worker":       { "backend": "openai-compatible", "model": "…",
                    "base_url": "http://localhost:11434/v1", "is_local": true },
  "orchestrator": { "backend": "openai-compatible", "model": "gpt-4o-mini",
                    "api_key_env": "OPENAI_API_KEY" }
}
# no seats block? byte-identical to before. opt in, or nothing changes.

Once the model is a commodity behind a fixed seam, you can optimize the seat. Measured on the harness's own judgment work, a small cheap model held its own against a flagship — and the swappable judge seat, when fed real repository context, made calls the same model couldn't make blind.

The pride bar

It refuses to ship what it can't verify

The wipe rule has a twin. If you assume the disk can lie to you, you also assume your own output can lie to you. An LLM's most dangerous failure isn't crashing — it's producing a confident, plausible, wrong result and shipping it. So the same humility that put state on disk put a verification gate in front of every claim: nothing merges until an independent pass confirms it's real.

That gate earns its keep by rejecting hallucinations — including its own most-wanted results. The clearest case is reflexive: the swappable-judge seam this note celebrates was, for its first several attempts, quietly broken. The early live measurements looked like clean wins. They weren't — the judge was being handed a dropped prompt, a mismatched schema, evidence that never actually reached it. Each "result" was an artifact of a seam that didn't work yet. Run after run, the verification layer flagged them as confounds and threw them out, rather than let a breakthrough get written into the story on false numbers. The seam only counted once it was truly wired; the real result — the 3/3 flip above — arrived after the near-misses were rejected, not instead of them. It came close, repeatedly, and refused to ship anyway.

The same discipline shows up everywhere the system grades itself. An all-cheap audit once reported four "critical" defects; every one was shown to be invented before a single fix was dispatched. A ladder of ten different models was put to one genuinely hard judgment, and the harness held the line rather than rubber-stamp a plausible answer. The bar is embarrassingly simple and rarely held: it does not ship known-broken, and it does not trust a result just because a model — even itself — sounded sure.

You saw the live version of this the day this note was written: a routine drift gate refused a documentation merge because a stat in the README didn't match the file it was generated from — off by a hundred-odd PRs. The number was wrong; the merge died; the number got fixed. Exactly as designed.

Why this matters now

The industry's hard problems have one shape

Every serious problem in shipping AI systems right now is a version of "you cannot trust the component to behave." Aesop's answer to each is not a new mechanism — it's the same primitive, pointed at a new failure.

Models are non-deterministic and crash
crash-onlyState lives on disk; a dead run is re-read and resumed, not lost.
Models hallucinate confidently
fail-closed gateNothing ships unverified; a plausible-but-false result is refuted, not merged.
Frontier inference is expensive
optimize the seatRun the cheapest model that's sufficient per seat; pay for judgment only where it counts.
The best model changes every month
narrow waistSwap the model behind the seam from config; the system doesn't notice.
No single model can be trusted alone
mechanism / policyNo one model is load-bearing. The state layer and the gates are — and those are just files and exit codes.

The bet Aesop makes is that the durable layer of an AI system should be the boring, inspectable, fifty-year-old part — plain files, git, exit codes — and the model should be the part you can rip out and replace on a Tuesday. That's not nostalgia. It's the only design that survives a component you fundamentally can't trust, whether the threat is a security agent deleting your disk or a language model inventing a fact.

Honest bounds

Single-instance is proven and shipped; the multi-instance coordination lifecycle (lease renewal, crash-orphan recovery, a repo-aware key) is scoped, scheduled work — documented, not hidden. The benchmark numbers are curated sets, not frontier parity claims, and every stat here is computed live from the repo and verifiable by cloning it. Aesop is source-available under PolyForm Strict — noncommercial, no-modify — not open-source.
